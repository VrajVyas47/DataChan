# DATA-CHAN V1 — Canonical MongoDB Database Schema Specification

## 1. Architectural Overview

Data-Chan V1 utilizes a MongoDB-First data model structured into two distinct, physically separated tiers:
1. **Platform Database (`datachan_platform`)**: The authoritative system store for all application metadata, user profiles, RBAC roles, workspace hierarchies, virtual database registrations, official curriculum practicals, learning progress, challenges, telemetry query history, forum discussions, and security audit logs.
2. **User Sandbox Databases (`dc_ws_<workspaceId>_db_<databaseId>`)**: Dynamically provisioned, isolated physical MongoDB databases. Sandbox collections and documents are user-created and decoupled from the fixed platform application schema, while MQL execution is strictly governed by AST parsing, whitelisted operations/operators, execution timeouts (`MAX_QUERY_EXECUTION_MS`), and result limits (`MAX_RESULT_DOCUMENTS`).

```
                              MongoDB Cluster
                                     │
         ┌───────────────────────────┴───────────────────────────┐
         ▼                                                       ▼
Platform Database: datachan_platform               Isolated Sandbox Databases
├── users                                          ├── dc_ws_ws_student_dev_db_vdb_student_dev
├── workspaces                                     │   ├── students (sample docs)
├── virtual_databases                              │   └── custom_collections...
├── classrooms                                     ├── dc_ws_ws_faculty_dev_db_vdb_faculty_dev
├── classroom_members                              │   └── ...
├── practicals                                     └── dc_ws_<userWs>_db_<vdbId>
├── lessons                                            └── ...
├── learning_progress
├── challenges
├── challenge_attempts
├── query_history
├── data_models
├── forum_posts
└── security_audit_logs
```

## 4. Multi-Tenant Sandbox Isolation & Execution Security Rules

### 4.1 Strict Namespace Derivation
- Physical MongoDB sandbox database names are derived exclusively server-side using the format `dc_ws_${workspaceId}_db_${databaseId}`.
- Clients supply only a logical `databaseId` (e.g. `vdb_...`). The API resolves this to `physicalNamespace` via `datachan_platform.virtual_databases` and verifies `vdb.userId === req.user.userId`.
- The client cannot supply arbitrary physical MongoDB database names (e.g. `admin`, `config`, `local`, or `datachan_platform`).

### 4.2 Query Validation & AST Parsing Enforcement
- All raw student MQL strings (e.g. `db.students.find(...)`) are parsed into an Abstract Syntax Tree (AST) using Acorn (`apps/api/src/security/queryParser.ts`).
- Only declarative literals (strings, numbers, booleans, null), arrays, and plain objects are evaluated.
- Function expressions, variable identifiers, `eval`, `process`, and arbitrary JavaScript execution are strictly blocked.
- Method chaining is strictly restricted to supported cursor methods: `.sort()`, `.limit()`, `.skip()`, and `.project()`.

### 4.3 Supported Operations & Operator Whitelisting
Sandbox execution is strictly restricted to an authorized V1 subset (`apps/api/src/security/operatorWhitelist.ts`):
- **Supported Operations (10)**: `find`, `findOne`, `insertOne`, `insertMany`, `updateOne`, `updateMany`, `deleteOne`, `deleteMany`, `aggregate`, `countDocuments`.
- **Allowed Filter Operators (20)**:
  - Comparison: `$eq`, `$ne`, `$gt`, `$gte`, `$lt`, `$lte`, `$in`, `$nin`
  - Logical: `$and`, `$or`, `$nor`, `$not`
  - Element: `$exists`, `$type`
  - Evaluation: `$regex`, `$options`, `$mod`
  - Array: `$all`, `$elemMatch`, `$size`
- **Allowed Update Operators (12)**:
  - `$set`, `$unset`, `$inc`, `$mul`, `$min`, `$max`, `$rename`, `$push`, `$pull`, `$pop`, `$addToSet`, `$currentDate`
- **Allowed Aggregation Stages (9)**:
  - `$match`, `$group`, `$sort`, `$project`, `$unwind`, `$limit`, `$skip`, `$count`, `$addFields`
- **Allowed Aggregation Expression Operators (18)**:
  - `$sum`, `$avg`, `$min`, `$max`, `$first`, `$last`, `$push`, `$addToSet`, `$multiply`, `$divide`, `$add`, `$subtract`, `$concat`, `$toLower`, `$toUpper`, `$substr`, `$cond`, `$ifNull`
- **Strictly Forbidden Operators**:
  - Code Execution: `$where`, `$accumulator`, `$function`, `$exec`
  - Arbitrary Evaluation: `$expr`
  - Multi-Collection Leaks & Writes: `$lookup`, `$out`, `$merge`

### 4.4 Resource Quotas & Limits
Configured in `apps/api/src/config/index.ts` and enforced in `playgroundController.ts`:
- **Execution Timeout**: Enforced via `.maxTimeMS(config.sandbox.maxQueryExecutionMs)` (default `5000ms`). Queries exceeding 5 seconds are terminated by the MongoDB engine.
- **Maximum Result Documents**: Enforced via `config.sandbox.maxResultDocuments` (default `100`). `find` queries cap limit at 100; aggregation pipelines automatically append `{ $limit: 100 }` if not present.
- **Maximum Document Size**: Enforced via `config.sandbox.maxDocumentSizeBytes` (default `1048576` bytes / 1MB) on `insertOne`, `insertMany`, and document APIs.
- **Batch Insert Cap**: `insertMany` in sandbox allows a maximum of 50 documents per call.
- **Pipeline Stage Cap**: Aggregation pipelines allow a maximum of 15 stages.

### 4.5 Destructive Operation Controls
- `dropDatabase` is completely blocked through playground query execution.
- Dropping a collection is only permitted via explicit collection management API routes (`DELETE /api/v1/databases/:id/collections/:name`), which verify database ownership.
- Deletions via `deleteOne` or `deleteMany` are executed strictly within the student's isolated physical database and subject to AST operator validation.
